# Goal 002: Controlled transformation diagnostics

## 調べる範囲

`gemm_smoke` の既知の C 変換、全要素ビット比較の結果、実際に実行した
カーネルの機械語、同じ環境での計測を候補 ID で対応付ける。
これは正式な PolyBench カーネルではない。全 run は
`environment_role="development_smoke"`、`publishable_benchmark=false` とする。

この段階では LLM の CPU 理解、複数 CPU の特化効果、移植性の総当たり、
IR / Assembly 入力最適化、提案手法の優位性を評価しない。
LLM API、モデル SDK、有料サービスは使わない。決定的に生成した候補を
LLM 生成候補と記録しない。コード差や高速化が出ることは合格条件ではない。

## 変換系列と正しさ

参照コードは `i → j → k` の順で、各 `c[i,j]` をゼロから単一の
累積変数に加算する。共通テンプレート `unroll_1` は
`i → j のブロック → k` とスカラーの端数ループを持つ。
展開率 `1, 2, 4, 8, 16` は、同じブロックで計算する独立した出力列数だけを変える。
各出力の積和は `k` の昇順を保ち、単一出力を複数の部分和へ分割しない。
配列の型と配置、入力、初期状態、ABI、フラグは全候補で共通であり、
展開率に応じた restrict、alignment、pragma や別アルゴリズムを追加しない。

ブロック条件は `n - j >= factor`。全体の列数より大きい展開率でも、
残りの全出力を共通のスカラーループが扱う。既存参照から共通テンプレートへの変更と、
共通テンプレート内の展開率変更を分けるため、コード比較の基準は次のようにする。

| 候補 | 生成元 | 実行コード比較の基準 |
|---|---|---|
| reference | 既存参照 fixture | reference 自身 |
| identity | 参照と同じソースの control | reference |
| unroll_1 | 決定的テンプレート | reference |
| unroll_2 / 4 / 8 / 16 | 同じ決定的テンプレート | unroll_1 |
| deliberately_wrong | 既存の誤候補 control | reference |

性能比の分母側候補と比較するペアの基準は、全候補で **reference** とする。
実行コード比較の基準と性能計測の基準は同一とは限らない。
候補数は参照を含め 8、正しい非参照の計測対象は通常 6。
全候補を計測前に manifest に固定し、遅い候補や同じ機械語の候補も保持する。

正しさは Goal 001 の有限 float64 入力、固定初期状態、全要素のビット比較を引き継ぐ。
`-O3 -fno-fast-math -ffp-contract=off` を維持し、許容誤差を緩めない。
デフォルトの検証サイズは `1,2,3,4,5,7,8,9,15,16,17`、seed は `1,17,42`。
展開率の境界、その前後、展開率より小さい条件を含む。
さらに実際の性能条件 `n=128,seed=17` と `n=256,seed=17` を加え、合計 35 条件を
各候補で計測前に検証する。これはテストによる検証であり、形式的同値性証明ではない。
検証失敗候補には計測ファイル、集計値、速度順位を作らず、失敗理由と生の検証出力を残す。

## 実行コードと最適化の証拠

Clang を使用し、同じ run では `CompilerTarget` を固定する。
CPU のプロンプト説明はコンパイラ設定を変更しない。
共通ドライバと各カーネルを別翻訳単位でコンパイルし、LTO を無効にし、
同じ `kernel` 関数名と ABI でリンクする。コマンドの全引数、ツールのパス・バージョン、
ソースの FP 関連指定、ソース・オブジェクト・実行ファイルの SHA-256 を保存する。
`-fsave-optimization-record` と `-foptimization-record-file` は実際のオブジェクト生成で使い、
非対応などのコンパイル失敗を成功として扱わない。

分析の正本は、検証および計測に使う `program` そのもの。
LLVM IR と Assembly は同じ設定による補助成果物であり、リンク後の実行コードとは区別する。
`llvm-readobj` の ELF 関数シンボル・サイズとセクションのファイルオフセットから
`kernel` のバイト列を抽出し、`llvm-objdump` が出した命令バイト列による
連続した全範囲の被覆と照合する。関数シンボルがない、曖昧、範囲が不正、
命令を読み取れないなどの場合は `analysis_unavailable` と理由を残す。
抽出は ELF x86-64 を対象とし、他形式への対応は主張しない。

共通ドライバのソースとリンク後の `main` の逆アセンブルから、時計呼び出し間の
対象カーネルへの直接呼び出しを確認する。これは静的な対応確認であり、
動的実行トレースではない。各実行時に記録したバイナリの SHA-256 と
分析対象の SHA-256 を対応付け、固定後のバイナリ変更は実行前に拒否する。

比較結果は `same_in_extracted_scope`、`different_in_extracted_scope`、
`analysis_unavailable` を区別する。判定は抽出した元の命令バイト列の SHA-256 と
サイズによる。実行ファイル全体のハッシュ差をカーネル最適化差とは呼ばない。
表示用の正規化は行頭の絶対アドレスを関数先頭からのオフセットへ変えるだけで、
バイト、即値、メモリ変位、分岐先オペランドを保持する。正規化テキストは比較判定に使わない。
元の逆アセンブルと抽出バイト列も保存する。

関数外のヘルパー、RIP 相対参照、間接制御移譲、オブジェクトの relocation を記録するが、
依存関係を再帰的には解決しない。従って完全一致や全プログラムの同値性を主張しない。
配置差によるバイト差もあり得る。コード差だけから意図した展開が残ったとは判断せず、
`intended_transformation_status="unknown"` を保持する。
命令数やコードサイズだけで速度を予測・断定しない。

最適化 YAML は原本とハッシュを保存し、Passed / Missed / Analysis の種類、
pass・remark 名、関数、原本の行位置、元の抜粋を保守的に索引化する。
Markdown は各種類で最初の異なる 3 件までを例示する。すべての記録は JSON / YAML に残る。
未解析・空・欠損の状態と理由を区別し、記録がないことを最適化されなかった証拠にしない。

## 測定フェーズと品質

デフォルトの性能条件は `128×128` と `256×256`、seed `17`。
これは開発用の小規模な 2 条件であり、将来の研究用ワークロードを代表するとは主張しない。
変更する場合は実行前に設定とサイズの選択理由を決め、新しい run を作る。

exploration と confirmation は、同じ固定済み候補・設定・バイナリで別々に実行する。
全ての検証済み候補を再測定し、exploration の結果で候補集合を選び直さない。
候補順は条件ごとに seed 付きでシャッフルする。デフォルト seed はそれぞれ
`2026002`、`2026003`。実行順とペア内の reference / candidate 順も保存する。
候補は直列に計測し、同一ユーザーの診断計測の重複をロックで防ぐ。
このロックはホスト上の他ユーザーや他アプリの負荷まで防がない。
affinity の要求値・適用結果・復元結果と、不成立時の理由を記録する。

各候補・条件・フェーズでウォームアップ 2 ペアと本計測 8 ペアを行う。
初期化、結果検証、出力をカーネルの計測区間外に置く。
各標本は新しいプロセスで初期状態をそろえ、一回のカーネル呼び出しを
`CLOCK_MONOTONIC` で計る。ウォームアップも別プロセスであり、
同一プロセスの定常状態を保証しない。短い計測には時計取得の影響があり得る。
検証、失敗、ウォームアップ、両フェーズの実行回数と壁時計時間は process ledger に残し、
セットアップやレポート作成などは operation の所要時間として記録する。

速度比は **同じ本計測ペアの reference 時間 / candidate 時間**。
1 より大きければそのペアで候補が速い。平均値の比や最短値ではなく、ペアごとの比とその中央値を保存する。
reference / candidate の時間それぞれに中央値、IQR、標本数などを保存する。
分位点はソート済み標本の `(N - 1) × p` の位置で線形補間し、`IQR=q75-q25` とする。
ウォームアップは集計から除外し、両フェーズの標本を混ぜない。
失敗、欠損、不完全なペア、無効な時間値は null の集計と理由を持つ。

品質基準は事前の設定と manifest で固定する。

| 設定 | デフォルト | 警告の条件 |
|---|---:|---|
| min_median_ns | 100000 | reference / candidate の中央値が閾値未満 |
| max_relative_iqr | 0.20 | 時間またはペア速度比の IQR / 中央値が閾値超 |
| rank_tolerance | 1 | 条件ごとの観測順位がフェーズ間で許容値を超えて変化 |
| near_tie_fraction | 0.03 | 隣接する速度比中央値の差 / 大きい側が閾値以下 |

順位は各フェーズ・条件ごとに有効な検証済み候補の速度比中央値の降順。
完全同率は同順位で、後続順位を飛ばす。reference には単独の架空の時間や順位を付けず、
各候補とのペア内で測定した基準として表示する。観測上の首位集合がフェーズ間で変わった場合も警告する。
品質警告は結果を消さずに保持する。観測最速を真の最適と呼ばず、統計的有意差も主張しない。
全候補が同等に見える結果、identity の比が厳密に 1.0 でない結果も通常の結果として扱う。

## 成果物と実行

WSL のリポジトリルートで、既存の仮想環境から実行する。

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m cpucond diagnose --output runs/goal002 --config configs/controlled-diagnostics.json
.venv/bin/python -m cpucond check-artifacts runs/goal002/<出力されたrun_id>
git diff --check
```

CPU 説明を明示する場合は `--spec-file configs/example-cpu-spec.txt` を指定する。
説明はホストから自動採用せず、none / spec のオフラインプロンプトだけに使用する。
CLI の `--cpu` は計測 affinity の指定であり、プロンプト条件とは独立している。

run ごとの `report.json`、`report.csv`、`report.md` が候補 ID によって
生成元、展開率、検証・失敗理由、実行コード比較と証拠、最適化記録、
フェーズ別の計測、順位、品質警告を結び付ける。CSV は候補 × フェーズ × 条件で 1 行、
未計測値は空欄、JSON は null。生標本は `phases/<phase>/` に分離して保存する。
設定、候補 manifest、計測前固定記録、全ソースとドライバ、ビルド・分析資料、
検証標準出力、runner の Python ソース、Git の commit / dirty 状態も保存する。
`experiment.json` の成果物 manifest と `check-artifacts` で整合性を確認する。

最終コードをローカルコミットしてから新しい run を作る。
修正が必要なら修正コミット後にさらに新しい run を作り直す。
旧 run は上書きせず、その Git 来歴を新 commit へ書き換えない。
プロンプトは共通 payload と CPU 説明をそれぞれハッシュで記録し、
none / spec では追加 CPU 説明だけを変える。性能値、順位、検証正解ラベルを含めない。
プロンプトの書き出しは LLM 実験ではない。候補選択は診断用であり、
将来の自由な C コード最適化を置き換えるものではない。

実際の LLM と 2 種類以上の CPU に進む前には、対象ホスト、自由生成の正しさ契約、
生成・探索予算、比較手法、探索と最終評価の分離、環境統制と統計手法を別途確定する必要がある。
これらを今回実施済みとは扱わない。
