# CPU条件付きLLM最適化の研究設計

Goal 001は、CPU情報の提示条件、実際のビルド条件、実機上の観測を分離し、正しさの検証を通過したC候補だけを計測するための基盤である。現時点の候補はすべて手書きのfixtureであり、LLMによる最適化、提案手法の新規性、CPU特化による性能改善は実証していない。

## 研究対象と比較の単位

研究の中心は、各CPUに適した最適化を選び、そのCPUの実機上で正しさと性能を評価することである。CPU情報がソースの変更に影響したか、その変更がコンパイル後にも残ったか、対象CPU上で有効だったかを順に調べる。

```mermaid
flowchart LR
    A[提示するCPU情報] --> B[最適化の選択とソース変更]
    B --> C[固定した条件でコンパイル]
    C --> D[生成コードの確認]
    D --> E[対象CPU上の正しさ検証]
    E --> F[対象CPU上の性能評価]
```

同一の実機内ではコンパイラの実体・バージョン・ターゲット・全フラグ・リンク設定、入力コード、正しさ契約を固定して提示条件を比較する。複数CPUへ展開する場合も、CPUごとにその実機内で比較する設計を基本とする。CPU間の移植性を総当たりで測る評価は今回の主目的に含めない。

今後の比較条件は次を予定する。プロファイルの種類、提案手法の具体的な仕組み、比較に使うLLMと生成予算はまだ確定していない。

| 条件 | 最適化へ与える追加情報 | Goal 001の実装範囲 |
| --- | --- | --- |
| CPU仕様の追加提示なし（`none`） | 共通のソース・実行契約・正しさ契約・出力形式 | ローカルでプロンプトを生成・保存する |
| CPU仕様の追加提示あり（`spec`） | 共通部分に加え、明示指定したCPU仕様文 | ローカルでプロンプトを生成・保存する |
| 通常のプロファイル誘導 | 実行時間、ホットスポット等の事前定義したプロファイル | 将来実装する比較対象。取得項目・提示方法を別途固定する |
| 提案手法 | CPU情報と診断結果を使う最適化選択の仕組み | 将来設計・実装・検証する。効果は未測定 |

`none`は追加のCPU仕様説明がない条件を意味する。ソースや共通契約に含まれるISA・ABIなどの情報まで完全に隠した条件とは呼ばない。通常のプロファイル誘導とコンパイラのPGOも区別し、後者を導入する場合は独立したビルド条件として事前に定義する。

## 情報と設定の分離

`HostObservation`には、実行時に観測したOS、カーネル、CPUモデル、プロセスが利用可能なCPU、ISAの表示、WSL・仮想化の表示を記録する。取得方法と欠測理由も保存する。WSLが表示するキャッシュ容量やコア数にはゲストから見える情報という範囲を付け、物理ホストの状態を推測して補わない。

`PromptCPUContext`は`none`または`spec`と、利用者が明示した仕様文だけを持つ。`CompilerTarget`は観測したコンパイラの実体・バージョン・デフォルトターゲットと、実際のビルド設定を持つ。これらの間に自動反映はなく、提示するCPU仕様を変えてもビルド条件は変化しない。デフォルトではCPU固有の`-march=native`なども自動追加しない。

プロンプトの許可入力は、ソース文字列、`PromptCPUContext`、共通の`ExecutionContract`だけである。ホスト観測全体、ホスト名、ローカルパス、コンパイラ診断を自動挿入しない。ソース文字列は明示した境界内へそのまま入れるため、利用者がソースや共通契約にCPU情報を書いた場合には両条件へ含まれる。

デフォルトの`spec`は「Example CPU、L1 32 KiB、L2 512 KiB」という合成の例示文であり、観測したホストの仕様ではない。実際の仕様を提示する場合は`--spec-file`で明示する。両プロンプトで変更するのは追加CPU仕様節だけで、同じ入力から同じ文字列とSHA-256を生成する。Goal 001ではどちらもLLMへ送信しない。手書き候補の計測を`none`対`spec`のLLM最適化実験として解釈しない。

## 実装したカーネルと正しさ契約

`gemm_smoke`は、この基盤のために作成した小さなfloat64行列積である。正式なPolyBenchカーネルや全30カーネル評価ではない。C11の`void kernel(size_t n, const double *a, const double *b, double *c)`を使い、重ならない行優先の配列に対して`c = a*b`を計算する。

候補は`reference`、同一ソースの`identity`、各出力の加算順を保ちながらループ構造を変更した`equivalent`、計算結果を意図的に変えた`deliberately_wrong`である。すべての出所を`handwritten_fixture`として保存する。

入力は32ビット符号なしLCGで実行時に生成する。`a`と`b`の値は`[-1, 1 - 2^-16]`の範囲で`2^-16`刻み、`c`の初期値は正のゼロである。サイズは`1..1024`、seedは32ビット符号なし整数を受け付ける。デフォルト検証はサイズ`1, 3, 8`とseed`1, 17, 42`の組合せで、計測に使うサイズ`64`・seed`17`も検証へ追加する。有限の検証集合であり、受け付ける全サイズ・全seedを網羅した結果ではない。

基準と候補の全`n*n`要素を、binary64のビット列を表す16桁の16進文字列で比較する。丸めた小数表示やchecksumだけで合否を判定しない。空出力、要素数不一致、形式不正、NaN・無限大を失敗として扱い、値の不一致とは区別して記録する。基準自体の実行・出力検証に失敗した場合も実験成功にはしない。独立したPythonの基準計算を使うCハーネスの統合テストも用意している。

共通のビルド条件は`-std=c11 -O3 -fno-fast-math -ffp-contract=off`で、`-ffast-math`や`-Ofast`は使わない。Clangの説明では、`-fno-fast-math`が危険な浮動小数点変換を無効化し、`-ffp-contract=off`が融合演算を禁止する。前者だけではFMA化を禁止する指定として足りないため、両方を明示する。参照した説明は[Clang 18.1.8 Users Manualの浮動小数点制御](https://releases.llvm.org/18.1.8/tools/clang/docs/UsersManual.html#controlling-floating-point-behavior)であり、実行したコンパイラのバージョンは各runで別途取得する。

ここでいう厳格な契約は、定義したスモーク入力についての出力ビット一致である。浮動小数点例外・動的丸めモードの全挙動を検証したものではなく、形式的な同値性証明でもない。今後、許容誤差を使う本実験へ進む場合は、入力領域、絶対・相対誤差等の比較方法、非有限値の扱いを独立した契約として定義する。

## 計測とその限界

検証を通過した`identity`と`equivalent`について、それぞれ基準実装とのペアを繰り返し計測する。ペア内の順序は反復ごとに基準→候補、候補→基準と入れ替える。ウォームアップと本計測は別のphaseで保存し、デフォルトはウォームアップ2ペア、本計測6ペアである。順序・反復番号・各計測値を保持し、本計測だけから中央値、最小・最大、MAD、母標準偏差、ペアごとの基準時間／候補時間を集計する。

各サンプルは新しいプロセスでカーネルを1回呼び出す。メモリ確保、入力生成、初期化、結果の利用と出力はカーネルを囲む`CLOCK_MONOTONIC`の区間外に置く。プロセス起動時間はカーネル時間へ含めない。毎回同じseedから配列を作り直すため、前回の出力状態を持ち越さない。カーネルとハーネスを別の翻訳単位でLTOなしにビルドし、区間後に全出力を読み込んでvolatileのsinkへ反映する。計測時のchecksumは処理の消去を防ぐためのもので、正しさ検証の代用品ではない。

ウォームアップも別プロセスであるため、同一プロセス内の繰返しによる定常状態を保証しない。カーネル呼出しやタイマーのコストは短い計測で無視できず、プロセスごとのアドレス配置、ページやキャッシュの状態、OS・ハイパーバイザーのスケジューリングによる変動も残る。ペアの順序を交互にするだけで、これらが除去されたとは扱わない。

CPU affinityは実際に利用可能な集合から選び、設定後に読み戻し、可否と理由を保存する。WSLの論理CPUへ固定できても、物理コアや周波数、Windows側の競合まで固定したことにはならない。root権限で周波数・turbo・SMTを変更しない。`perf`はGoal 001で使用せず、その不使用理由を記録する。

WSLでのrunは`environment_role="development_smoke"`、`publishable_benchmark=false`とする。これらのラベルは測定品質の保証ではない。速度比はパイプライン動作の確認用であり、CPU特化の有効性や論文の主要結果として報告しない。

## 実行コードと再現記録

一意のrunディレクトリに、設定・スキーマ・Git状態、ホスト観測、コンパイラの実体と全ビルド引数、ソースのコピーとSHA-256、両プロンプトとSHA-256、ビルド診断、検証条件と結果、生の計測値、集計を保存する。環境変数全体や認証情報は記録しない。プロセスには`PATH=os.defpath`、`LANG=C`、`LC_ALL=C`だけの環境を渡す。

ClangでC候補からLLVM IRとAssemblyを出力し、リンク後の`kernel`シンボルを逆アセンブルする。これらはC入力をコンパイルした分析用成果物である。`input_kind`は`c`、`llvm_ir`、`asm`を区別し、現時点で未実装のIR入力・Assembly入力の候補評価は明示的に拒否する。

成果物のSHA-256は保存されたファイルと記録の対応を確認する。ソース、IR、Assembly、実行ファイルのハッシュやテキスト差分だけでは、意味的同値性や性能差の原因を確定しない。今後は変更した命令・アクセス・ループ構造が生成コードに残ったかを確認し、対象CPUでの診断や対照実験と結び付ける必要がある。

誤った候補には計測を実行せず、計測結果を`null`のまま残す。コンパイル失敗、異常終了、timeout、出力形式不正、値の不一致は分類し、失敗した数値計測を0秒や架空の速度比で補わない。正しいfixtureの検証・計測、誤りfixtureの期待どおりの拒否、成果物整合性を確認してからrunの成功を扱う。

## 将来の生成・探索・最終評価

LLM生成のばらつきと計測のばらつきを分けて扱う。各条件で複数の独立した生成を行い、モデル・プロンプト・生成設定・候補IDを記録する。そのうえで各候補を複数回計測し、候補間の差と同じ候補の計測誤差を分離する。1回の生成結果へ多数のタイミング測定を追加しただけで、生成の再現性を評価したことにはしない。この生成実験はGoal 001には含めない。

探索用の計測は候補の選択や修正に使い、最終評価用の計測は選択済み候補と評価条件を凍結して別に行う。最終評価の結果を見て選択し直す場合は、その評価を探索へ数え、新たな最終評価を必要とする。入力・seed・計測順序・反復回数・停止条件と、失敗や外れ値の扱いを事前に定義し、最良の単発計測だけを採用しない。

比較条件には共通の探索予算を設定する。LLM生成回数やトークンだけでなく、候補のビルド、正しさ検証、計測、追加診断、コンパイル失敗、誤り候補、timeout、修復・再試行に使った費用も数える。費用の単位と上限は本実験前に決め、成功候補だけを残した費用比較を避ける。現実装はこれらの工程の記録を行う基盤であり、LLM費用計算や探索予算管理機能は未実装である。

## Goal 002へ進む前に

次段階では、対象CPUの実機と本計測条件を確定し、通常のプロファイル誘導・提案手法・評価予算を具体化する必要がある。カーネルや入力領域の拡張、必要な正しさ契約、LLM生成の独立反復、探索と最終評価の分離、短時間カーネルに適した計測方法、生成コードの変化と性能を結ぶ診断を順に実装・検証する。

現時点で扱えるのは、自己完結したCの手書きfixtureを使った開発スモークである。旧資産の監査範囲と未確認事項は[legacy-audit.md](legacy-audit.md)、ローカルの実行手順は[README](../README.md)を参照する。
